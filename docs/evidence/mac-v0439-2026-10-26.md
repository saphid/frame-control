# Official Intel Mac release test, 26 October 2026

Physical **MacBookAir9,1, Intel Core i3 1.1 GHz, macOS 15.7.7 (24G720)**.
The earlier ARM64 failure led to [#262](https://github.com/saphid/frame-control/pull/262),
now merged. This test uses the published **v0.4.39**, tag `fd0b0a9`, rather
than the locally built candidate. [Earlier results](mac-desktop-2026-10-26.md)
remain a separate historical record.

## Download, installation and Gatekeeper observations

Downloaded `Frame-Control-mac-x64.dmg` and its same-release `SHA256SUMS`
with `gh release download`. `shasum -a 256 -c SHA256SUMS --ignore-missing`
passed for the downloaded asset:

```text
f47b5a188b5090f97a72467394d4fa65ccc73fe3169a6276e2a32cab5c8019d8  Frame-Control-mac-x64.dmg
```

Also clicked that asset in T3's Chromium browser. Its 169,230,398-byte download
had the same hash. **Neither download had `com.apple.quarantine`.** T3's
browser is not evidence of Safari/Chrome download metadata.

Mounted the verified CLI DMG read-only, preserved the task's earlier ARM64
installation, and copied `Frame Control.app` into `/Applications` with `ditto`
(the command-line equivalent of dragging it there). The executable is x86_64;
`codesign -dv` reports ad hoc signing. `open "/Applications/Frame Control.app"`
returned success and the app started its bundled Python server.

**No Gatekeeper warning dialog was observed.** `spctl --assess --type execute
-vv "/Applications/Frame Control.app"` returned exit 3 and exactly:

```text
/Applications/Frame Control.app: rejected
```

Opening this unquarantined copy needed no override. This does not establish
the warning or opening steps for a quarantined browser download. The README
keeps Apple's Open Anyway guidance, explicitly unverified here. No quarantine
attribute was removed and no global security setting was changed. System
Events inspection timed out; an AppleEvent quit request returned “User
cancelled” (-128). Native console/menu automation remains unavailable.

## Official native app results

After the normal launch, a second run disabled telemetry, used a task-local
server data directory and enabled a temporary loopback renderer debug port.
The app bundle was not patched. The following checks used its real renderer
and `window.frameApp` IPC bridge; they are not physical mouse/menu tests.

| Check | Result and limit |
|---|---|
| UI | Apps, Games, Tools, Settings, Privacy & updates, Capture and Decky views rendered with the expected headings. The activity log showed the stale SSH identity warning. [Native Apps screenshot](mac-v0439-native-2026-10-26.png) |
| Settings | Initial native preferences were `{}`. `mvSeparate="0"` saved and read back, including after a real app restart. The original preferences file was restored byte-for-byte in `finally` (or removed if originally absent) |
| Open at Login | Still opt-in in source; no login item was enabled. Actual menu checkbox and OS login behavior remain unverified because native automation was unavailable |

| Framey preview | No standalone local Framey preview control found. No VR runtime result claimed |

Closing the app through `window.close()` stopped its processes and closed
the debug port. **The final shutdown log exposed a bug:** stdin EOF and the
app's SIGTERM can overlap, raising `KeyboardInterrupt` while cleanup is
installing its ignore handler. Cleanup can then stop before releasing staging
or SSH resources. [#284](https://github.com/saphid/frame-control/pull/284)
changes SIGTERM to request HTTP shutdown without raising into cleanup.

The regression test injects SIGTERM at that exact cleanup boundary. On this
physical Mac with the official app's bundled Python 3.12, it failed before
the fix with exit -2 and the observed traceback. After the fix, all **45
server integration tests** passed, including owned staging-file cleanup.
This validates source from the fix PR, not a fixed published app.

## Headset relay and small transfer

`frame.local` resolved but TCP 22 returned **No route to host**. The native
app refused a stale SSH identity; no pin was replaced. The trusted lxso2
coordinator relay could reach the Frame. Both shared locks were absent.

The relay test atomically created `/tmp/frame-test.lock` on the coordinator
and the headset, each with this job's owner marker. It then:

- Read battery **99%, Not charging** before and after; storage total
  **996,984,774,656 bytes**, free **769,077,035,008 bytes**.
- Listed **7** Steam screenshot JPEGs matching
  `userdata/*/760/remote/*/screenshots/*.jpg`; no image was copied. This narrower
  layout-specific count differs from the earlier broad JPEG search.
- Sent a **40-byte** test payload from this Mac through lxso2, created one
  reserved file in the Frame user's home using exclusive creation, and read
  it back. SHA-256 matched
  `457485db13f80d819d5301d337502c3df050c6b3eb6202be7aac85d2af8e0b92`.
- Deleted that exact test file and released only the matching owned locks.
  A separate SSH read verified the file and both locks were absent.

This proves a bounded relay transfer, not native Mac app file transfer or
direct `frame.local` connectivity. No existing headset file, app, service,
power setting or SteamVR state was changed. The headset was not wiped or
rebooted. Real OBS and wearer/controller interaction remain unverified.

The DMG was ejected; the native app, debug port and task browser tab were
closed; the desk hold was released. The official app remains installed for
reproduction. No social post was made; PR #113 was left alone.
